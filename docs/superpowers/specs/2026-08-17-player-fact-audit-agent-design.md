# 球员全项目事实审计智能体设计

## 目标

为 `daily-star` 建立一套可由 Codex 重复执行、支持断点续跑的球员事实审计工作流。审计覆盖项目内全部球员及其所有相关数据，不以 CSV 为边界。智能体逐名联网核验，自动修正确认错误，重新生成下游数据，并为每项结论保留证据和审计记录。

## 审计范围

审计覆盖以下信息：

- 身份：中文名、英文名、别名、国籍、出生日期、身高、惯用脚、位置、号码和现役状态。
- 生涯：青训、一线队、租借、回归、转会日期、自由身阶段、当前俱乐部和退役时间。
- 成就：俱乐部荣誉、国家队荣誉、个人奖项、亚军或入选经历，以及代表比赛。
- 数据：赛季出场、首发、进球、助攻、国家队出场与进球、历史身价及其统计口径。
- 内容：标签、简介、技术特点、八条线索、时间线、俱乐部摘要、代表比赛和冷知识。
- 资源：球员头像、俱乐部队徽、国家队标志、资源路径、供应方主键和展示映射。
- 派生产物：CSV、SQLite、`apps/web/src/generated/` 下的文件及前端展示数据。

## 数据分层与修改原则

项目数据分为三层：

1. `data/` 中的身份、履历、统计、内容和资源清单是主要源数据层。确认错误应优先在此修正。
2. CSV、SQLite 和 `apps/web/src/generated/` 是生成层。修改源数据后通过项目脚本重建，不零散修补生成结果。
3. 前端代码中的球员资料和资源映射是展示层。与源数据冲突时，应修正或迁移硬编码内容，避免形成第二事实源。

审计必须保留用户已有的未提交改动。只修改已确认属于球员事实、数据一致性或资源归属问题的内容，不顺带重构无关代码。

## 审计流程

每名球员按以下顺序处理：

1. 以 `slug` 为主键汇总项目中的身份、履历、统计、内容和资源引用，先发现内部冲突。
2. 核验身份与当前状态。
3. 核验完整俱乐部路线，区分青训、一线队、租借、回归和自由身，并检查日期倒置、无依据重叠及缺失阶段。
4. 核验球队荣誉与个人奖项，明确区分冠军、亚军、赛事奖项、最佳阵容和普通参赛经历。
5. 核验赛季、国家队和身价数据；记录数据供应方及覆盖范围，不混合不同赛事或出场口径。
6. 核验所有中文内容，并同步修正受事实错误影响的简介、线索、时间线、代表比赛和冷知识。
7. 检查头像是否为本人，队徽与俱乐部 ID 是否匹配，国家队标志是否正确，以及本地资源是否存在并可读取。
8. 修改权威源数据，运行对应同步或导入脚本，重建全部下游数据。
9. 运行一致性校验、项目测试、生产构建和浏览器抽查，写入该球员的最终审计状态。

每完成一名球员即持久化进度。中断后从未完成球员继续，不重新审计已经通过且相关源文件未变化的球员。

## 证据与决策规则

来源优先级如下：

1. 官方俱乐部、国家队、联赛、国际足联、洲际足联和赛事组织。
2. Transfermarkt、Statbunker 等与当前字段口径匹配的可靠数据库。
3. 可靠百科、通讯社和主流媒体，用于补充生涯故事、代表比赛和冷知识。

确认事实至少满足以下条件之一：

- 一个直接支持该字段的官方来源；
- 两个相互独立且口径一致的可靠来源。

动态信息必须记录核验日期。若来源冲突、网页失效、统计口径不兼容或证据不足，智能体不得猜测或以更流畅的叙述替代事实。此类条目保留当前值并标记为 `待复核`，报告冲突来源和原因。明确错误标记为 `已修改`，无问题条目标记为 `已通过`。

## 组件

### Codex 审计说明

项目内提供专用的 Codex 工作说明，规定输入、逐人流程、搜索和证据规则、允许修改的文件、生成命令、验收门槛及断点续跑方式。它不依赖独立的 OpenAI API 密钥，由用户在 Codex 中启动和执行。

### 审计状态

机器可读状态文件按 `slug` 保存：

- 状态：`待审计`、`已通过`、`已修改` 或 `待复核`。
- 审计时间和所依据的源文件指纹。
- 检查过的字段类别。
- 每项问题的旧值、新值、原因、证据 URL、来源标题和置信度。
- 修改及重新生成的文件。
- 尚未解决的冲突或阻塞原因。

状态文件只记录审计事实，不复制整份球员数据库。

### 自动一致性校验器

校验器负责可确定性判断，不代替联网事实核验。至少检查：

- 各数据文件的球员主键、姓名和数量一致。
- 日期格式、先后顺序、俱乐部阶段重叠和当前状态一致。
- 荣誉分组总数与明细计数一致，年份和次数无明显矛盾。
- 相同统计字段的数据来源和覆盖范围明确。
- 简介、线索、时间线、俱乐部摘要与结构化数据不存在直接冲突。
- 线索不直接泄露姓名，且同一球员的线索不重复。
- 头像、队徽、国家队标志文件存在，资源主键和俱乐部映射可解析。
- 源数据与 CSV、SQLite、前端生成文件之间不存在生成漂移。

校验器输出 JSON 结果和非零失败码，便于 Codex 定位到球员、字段和文件。

### 审计报告

生成 Markdown 汇总和机器可读明细。汇总包含球员总数、通过数、修改数、待复核数、按类别的问题统计和未解决项。每名球员的明细列出修改前后、证据、置信度和受影响文件。没有变更的球员仍保留完成记录，保证没有静默跳过。

## 错误处理

- 网络或网站暂时不可用时记录失败来源，尝试同级替代来源；证据仍不足则标记待复核。
- 来源对转会生效日、赛季归属或出场口径定义不同时，保留供应方原始口径并在报告中说明，不强行合并。
- 图片只能确认文件存在但无法确认人物或徽标归属时，不自动替换，标记待复核。
- 同步脚本、测试或构建失败时，该球员不能标记完成；状态中记录失败命令和影响范围。
- 若拟修改文件包含用户的重叠改动，先基于当前内容做最小修改；无法可靠合并时停止该条并报告，不覆盖用户工作。

## 验收标准

1. 项目球员名单中的每个 `slug` 都有审计状态，且不存在未说明的跳过项。
2. 每个 `已修改` 结论都有旧值、新值、原因和符合规则的证据。
3. 每个 `待复核` 结论都明确记录冲突或证据不足原因。
4. 源数据修正后，所有相关生成文件、CSV 和 SQLite 均通过项目脚本重建并保持一致。
5. 自动一致性校验、现有项目测试和生产构建全部通过。
6. 浏览器抽查覆盖传奇与现役球员、不同位置、不同知名度和不同资源类型；头像、队徽、国家队标志、荣誉、生涯路线、统计和线索均正确显示。
7. 原有未提交改动得到保留，审计不引入无关重构或格式化噪声。

## 非目标

- 不建立脱离 Codex 独立运行的联网大模型服务。
- 不以单一网站作为所有字段的唯一事实源。
- 不在证据不足时补写荣誉、统计、转会或冷知识。
- 不借审计工作重做游戏玩法或界面设计。
